## What it does

A small business has dozens of standing promises: rent, loan EMIs, salaries, GST, supplier bills going out, and
client retainers and invoices coming in. Each one is easy to track alone. The problem is the day they collide and
the bank balance is not enough.

FCIS records every commitment once, expands it into dated instalments, and projects each bank account day by day.
When the projected balance is about to fall below the account's safe level it raises a shortfall alert, weeks ahead,
and lists which negotiable payments could be deferred to close the gap.

It is more than CRUD:

- **Instalments are generated by a trigger** from a recurrence rule (weekly, monthly, quarterly, yearly, once).
- **Money only moves through stored procedures.** No role can insert into the ledger directly; a trigger keeps
  balances in step and a CHECK constraint refuses anything below the overdraft limit.
- **Forecasting is done in SQL**: a recursive CTE builds the calendar, a window function builds the running balance,
  receipts are weighted by each payer's reliability, and gaps-and-islands logic groups shortfall days into alerts.
- **What-if simulation**: re-project an account with one payment moved, without writing anything.
- **Role-based access is enforced by PostgreSQL**, not only by the UI. The app logs in as a role with no rights and
  must `SET ROLE` per request.
- **MongoDB holds what does not fit tables**: free-form contract terms, the full forecast curve of every run as one
  document, and the activity stream.

### Why two databases

| Data | Store | Reason |
|---|---|---|
| Accounts, commitments, instalments, ledger, alerts, users | PostgreSQL | Money needs ACID transactions, foreign keys, CHECK constraints and joins. A payment must update the ledger, the balance and the instalment together or not at all. |
| Notes and contract terms | MongoDB | Every commitment has different terms (a lease has `graceDays` and `escalationPercent`, a loan has `penalInterestPercent`). A flexible sub-document avoids a sparse table or an EAV design, and a weighted text index searches title, tags and body. |
| Forecast snapshots | MongoDB | One run produces 61 days per account, each with the list of instalments behind it. It is written once, read whole to draw a chart, and never joined. One nested document replaces hundreds of rows. |
| Activity stream | MongoDB | Events have a different payload per type and expire by themselves through a TTL index. |

## Setup

Prerequisites: Node.js 20.9 or newer, PostgreSQL 15 or newer, MongoDB 6 or newer, all running locally.

```bash
git clone https://github.com/vishalprasath/dbms-miniproject-fcis.git
cd dbms-miniproject-fcis
npm install
cp .env.example .env.local
```

Edit `.env.local`:

- `PG_ADMIN_URL`: a PostgreSQL superuser connection, used only by the setup script.
- `DATABASE_URL`: keep the user as `fcis_app` and choose any password; the setup script sets it.
- `MONGODB_URI`: your MongoDB connection string.
- `AUTH_SECRET`: 32 or more random characters, for example from `openssl rand -hex 32`.

Then build both databases and start the app:

```bash
npm run db:setup
npm run dev
```

Open http://localhost:3000.

`npm run db:setup` creates the `fcis` database, runs `db/sql/01` to `06` in order, sets the password of the login
role, then creates the MongoDB collections, validators, indexes and seed documents. It is safe to run again: it
rebuilds everything from scratch.

## Database design in brief

Ten tables in schema `fcis`: `users`, `bank_accounts`, `categories` (self-referencing), `counterparties`,
`commitments`, `commitment_schedule`, `transactions`, `forecast_runs`, `shortfall_alerts`, `audit_log`.
See `docs/er-diagram.png` and the report for the ER diagram, relational schema and data dictionary.

### Advanced SQL features used

| Feature | Where |
|---|---|
| Stored procedures | `sp_record_payment`, `sp_transfer_funds`, `sp_post_transaction`, `sp_defer_schedule`, `sp_run_forecast`, `sp_generate_schedule`, `sp_mark_overdue`, `sp_create_user`, `sp_reset_password` |
| Functions | `fn_project_cashflow` (table function), `fn_suggest_deferrals`, `fn_alert_severity`, `fn_nth_due_date`, `fn_verify_login`, `fn_app_user` |
| Triggers | instalment generation, status derivation, ledger to balance, immutable ledger, commitment guards, last-admin guard, audit trail |
| Transactions | every request is one transaction; payments and transfers are atomic; savepoints in tests |
| CTEs and recursion | calendar in `fn_project_cashflow`, category tree roll-up, gaps-and-islands for alerts |
| Views | `v_upcoming_dues`, `v_account_health`, `v_monthly_cashflow`, `v_counterparty_exposure`, `v_live_alerts`, `v_user_directory` |
| Indexing | B-tree, partial, expression and GIN indexes |
| Full-text search | generated `tsvector` column with weights on commitments; expression index on ledger narration |
| Role-based access | four roles, table and column-level GRANTs, SECURITY DEFINER routines |

### MongoDB features used

`$jsonSchema` validation, compound / multikey / text / unique / partial / TTL indexes, CRUD with `$set`, `$push`,
`$addToSet`, `$currentDate`, and aggregation pipelines with `$unwind`, `$group`, `$dateTrunc`, `$cond`, `$replaceRoot`.

## How access control works

1. The app connects as `fcis_app`, a `NOINHERIT` login role that can execute `fn_verify_login` and nothing else.
2. Login calls `fn_verify_login(email, password)`, which compares a bcrypt hash inside the database.
3. Every later request runs in one transaction that starts with `SET LOCAL ROLE fcis_viewer | fcis_analyst | fcis_admin`
   and `set_config('app.user_id', ...)`.
4. PostgreSQL then allows or refuses each statement. A refusal (SQLSTATE 42501) becomes HTTP 403.

The Administration page shows the live privilege matrix read from `has_table_privilege()`.
